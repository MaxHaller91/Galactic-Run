# Yuka AI Library: Behaviors and Three.js Integration

## Overview of Yuka and Agent Behaviors

**Yuka** is a standalone JavaScript library for Game AI that provides a variety of AI behavior components and is designed to integrate with any rendering engine (commonly Three.js). It implements **autonomous agent** concepts based on video game industry best practices. Yuka’s core features include: a **vehicle/agent model** with built-in **steering behaviors**, a **finite state machine** system, graph-based **pathfinding** (with waypoints and navigation meshes), agent **perception** (vision and memory), and a messaging/trigger system for interactions. All game logic runs in Yuka’s world, independent of Three.js, and you sync the results to your Three.js scene for visualization.

### Steering Behaviors

Yuka comes with many **steering behaviors** that can be combined to create complex movement for agents (instances of `YUKA.Vehicle`). Each steering behavior produces a directional force (vector) that the vehicle uses to adjust its velocity. You can add multiple behaviors to a vehicle’s steering manager and assign weights to blend them. Some key steering behaviors include:

* **Seek:** Steers the agent to move **toward a target position**. This generates a force that points the agent at the target.
* **Flee:** Steers the agent to **escape a target position**, i.e. move away from a threat. (Yuka also provides an **Evade** behavior, which is like a predictive flee used to avoid a *pursuing* agent.)
* **Arrive:** Causes the agent to move to a target but **decelerate as it approaches**, so it comes to a smooth stop at the destination. You can usually specify a deceleration rate or tolerance for stopping.
* **Pursuit:** Steers an agent to **intercept a moving target**, predicting the target’s future position. This is useful for chasing moving entities (e.g. a missile homing in on a ship).
* **Obstacle Avoidance:** Steers the agent to **avoid obstacles in its path**. The vehicle will attempt to steer around any solid obstacles (you define obstacles as Yuka entities with a position and bounding radius).
* **Wander:** Causes a vehicle to **wander randomly** in the environment. This produces a semi-random steering force that gives a natural drifting or patrolling movement.
* **Other behaviors:** Yuka includes many more, like **Cohesion, Alignment, Separation** (the three combined in classic **flocking** behavior), **FollowPath** (follow a series of waypoints), **OffsetPursuit** (follow a leader at an offset for formations), **Interpose** (move to a point between two agents), and **Hide** (not explicitly listed, but can be implemented using combinations of evade and obstacle checks). These behaviors can be mixed and matched by adding them to an agent. For example, a “flocking” agent might have **Alignment**, **Cohesion**, and **Separation** added together to move as a group. Each behavior has an `active` flag and a `weight` that you can tune to adjust its influence.

**Usage example:** To use steering behaviors, you typically create a vehicle and one or more behaviors, then add them to the vehicle’s `steering` manager. For instance, to make a ship seek a moving target but also avoid obstacles:

```js
// Create agent and target
const vehicle = new YUKA.Vehicle();
vehicle.maxSpeed = 5;                   // set max movement speed
const targetEntity = new YUKA.GameEntity();
// ... set targetEntity position ...
// Define behaviors
const seek = new YUKA.SeekBehavior(targetEntity.position);
const avoid = new YUKA.ObstacleAvoidanceBehavior(obstaclesArray);
// Add behaviors to vehicle
vehicle.steering.add(seek);
vehicle.steering.add(avoid);
// Optionally adjust weights
seek.weight = 0.8;
avoid.weight = 1.2;
```

In this snippet, `obstaclesArray` would be an array of Yuka entities representing obstacles (each with a position and a bounding radius) and `targetEntity.position` is a reference to the target’s position vector. Yuka will internally sum the forces from Seek and ObstacleAvoidance (considering the weights) to compute the steering for the vehicle each update. Steering behaviors update the `vehicle.velocity`; Yuka’s **locomotion model** then moves the vehicle’s position each frame based on that velocity. This means the movement is smooth and governed by realistic parameters like mass, maxSpeed, and maxForce that you can set on the vehicle.

### Finite State Machines (FSM) for Agent AI

Beyond low-level movement, Yuka supports higher-level decision logic via **finite state machines**. Each agent can be assigned a `StateMachine` (Yuka provides a `YUKA.StateMachine` class) managing a set of states (each state is a subclass of `YUKA.State`). This is useful for implementing modes of behavior (patrolling, attacking, fleeing, docking, etc.) and switching between them based on conditions.

**Defining states:** You create custom state classes by extending `YUKA.State` and implementing the `enter(agent)`, `execute(agent, delta)` and `exit(agent)` methods. For example, a spaceship might have states like **PatrolState**, **ChaseState**, **DockState**. In `execute()`, you define what the agent does in that state (e.g. apply certain steering behaviors or issue commands), and you can check conditions to trigger a transition to another state. To perform a transition, you call the state machine’s `changeTo(stateName)` method.

**Using the state machine:** Typically you attach a `StateMachine` to the agent and register all possible state instances with it. For example:

```js
const ship = new YUKA.Vehicle();
ship.stateMachine = new YUKA.StateMachine(ship);
ship.stateMachine.add('PATROL', new PatrolState());
ship.stateMachine.add('CHASE', new ChaseState());
ship.stateMachine.add('DOCK', new DockState());
ship.stateMachine.changeTo('PATROL');  // start in PATROL state
```

Now the ship’s state machine will call the current state's `execute()` on each update. Within a state’s logic, you might do something like `if (ship.seesEnemy) ship.stateMachine.changeTo('CHASE')`. You can also define a **global state** (executed on every update regardless of current state) or previous state to allow “revert to previous” transitions. Yuka’s FSM system also supports messaging: states can implement an `onMessage(agent, telegram)` method and agents can send messages to each other (using `entity.sendMessage`) which the state machine routes to the current state. This is useful for team coordination (e.g. one AI can send a message like “Help me!” to trigger allies to transition to an assist state).

**Example scenario:** Yuka’s examples include a simple FSM where an entity switches between an “IDLE” and “WALK” state continuously, as well as a more complex **Space Carrier** example where a spaceship collects artifacts until it’s full, then enters a “return to base” state to unload, and repeats. These demonstrate how states can manage an agent’s high-level behavior sequence. In a space combat game, you could implement states such as *Patrol*, *EngageEnemy*, *Flee*, *DockForRepair*, and use conditions (health low, enemy spotted, etc.) to transition between them in a clean, organized way.

### Pathfinding and Navigation

For navigating in structured environments (or avoiding expensive continuous steering), Yuka provides **pathfinding** utilities. It has a generic graph implementation (`YUKA.Graph`) and search algorithms like **A\*** and **breadth-first search** built in. This allows you to create waypoint graphs or grids and find optimal paths between nodes. For example, you can construct a graph of space stations or jump gates and use A\* to find the best route for a trading ship’s hyperspace jump sequence.

In addition, Yuka includes a **Navigation Mesh** system: you can define a navmesh (as interconnected convex polygons) representing walkable or flyable space, and use Yuka’s pathfinding on that mesh. The library provides `NavMesh` and `NavMeshLoader` classes to work with navigation meshes (for instance, you might export a navmesh from a modeling tool or generate one for an asteroid field). An example on the Yuka site shows an agent constrained to a navmesh for movement. With a navmesh, Yuka can compute a path on the mesh and even subdivide the path into waypoints the vehicle can follow with a **FollowPathBehavior**.

For dynamic avoidance of obstacles and other agents, Yuka’s steering behaviors (like ObstacleAvoidance) handle local collision avoidance. But if you have many moving entities or need efficient range queries, Yuka offers **spatial partitioning** structures. The `YUKA.CellSpacePartitioning` class implements a 3D grid of “cells” to quickly lookup nearby entities. You can assign an `EntityManager.spatialIndex` (either a cell space or a BVH) to have the engine automatically manage entity positions in a spatial index. This greatly improves performance for neighbor queries in flocking or finding nearby obstacles, because Yuka will check only entities in nearby cells instead of every entity. The **NavMesh (Advanced)** example combines a navmesh with a spatial index and Yuka’s task system to handle many agents efficiently.

### Group Behavior and Team Coordination

Yuka supports basic **group behaviors** out of the box. The primary example is **flocking**: using **Alignment**, **Cohesion**, and **Separation** behaviors together causes a group of vehicles to move as a coherent flock (Alignment makes an agent match the heading of neighbors, Cohesion steers it toward the center of neighbors, Separation spreads them apart to avoid crowding). There is even a convenience `FlockingBehavior` in the examples which is essentially a combination of those three. You can adjust each component’s weight to get tighter or looser formations.

For **formations** or team maneuvers, Yuka provides the **Offset Pursuit** behavior: one agent can act as a leader and others pursue a point offset from that leader, maintaining a formation (e.g. a wingman staying at a fixed offset relative to a leader ship). There’s also **Interpose**, which can be used by a team member to position itself between two entities (for example, a friendly ship interposing itself between an ally and an enemy fire).

Beyond steering, **communication and coordination** can be handled via Yuka’s messaging system and triggers. Agents can have a **short-term memory** and **vision sensors**: Yuka’s `Vision` class can be added to a vehicle to test line-of-sight and field-of-view for detecting other entities. If one agent spots an enemy or important event, you could use `agent.sendMessage()` to notify others. Yuka’s `EntityManager` will route messages to the recipient’s `handleMessage`, which typically passes it to the agent’s state machine (`StateMachine.handleMessage` invokes the current state’s `onMessage`). This allows your AI team to coordinate (e.g. “Enemy at sector 7” message could make all ships switch to attack mode).

Yuka also supports **Trigger** objects that can be placed in the world; when an agent enters a trigger region, it can cause some event (for example, entering a “station proximity” trigger could signal a ship to initiate docking procedure). These are useful for coordinating behavior with locations or zones.

### Extending Yuka for Custom AI Behaviors

One of the strengths of Yuka is that it is **extensible** – you can create new behaviors or tailor existing ones, which is particularly useful for specialized scenarios like space combat or trading simulation. Yuka’s design is somewhat “concrete” (as one user noted, you work with Yuka’s provided classes directly), but you *can* extend them. For example, to create a custom steering behavior, you can subclass `YUKA.SteeringBehavior` and override its `calculate(vehicle, force)` method to produce your own steering force. Developers have successfully added new behaviors this way – for instance, one developer implemented a **flow-field pathfinding** behavior as a custom steering force, allowing agents to follow a flow field combined with other behaviors.

In a space game, you might need to extend Yuka for true 3D movement. Out-of-the-box, some steering behaviors assume movement on a 2D plane (X-Z plane); for example, the Wander behavior by default might only perturb heading in a horizontal circle. In a 3D space environment, you can create a version of Wander that also changes vertical direction. Users have reported that making Yuka fully 3D for flight is feasible – *“Fortunately it’s easy to extend”*. One user added a custom behavior to confine flocking birds within a sky volume (so they don’t wander off infinitely). Similarly, you might create a **KeepInBoundsBehavior** for spaceships to stay within a sector, or an **AttackRunBehavior** that dictates a strafing attack pattern (which could internally combine a path and a firing trigger).

Yuka also includes a **fuzzy logic module** (classes for fuzzy sets, rules, etc.), which can be used to build AI decision-making like target or weapon selection. This might be useful in a trading AI for evaluating profit factors or in combat AI for choosing when to engage or flee. Additionally, Yuka’s **Goal-Driven** agent design (goal/subgoal hierarchy) can be used for complex behaviors like a trading ship’s mission planning: you can set a top-level goal like “MakeProfit” which spawns subgoals to travel to a station, dock, buy goods, travel elsewhere, sell goods, etc. The `CompositeGoal` and related classes support stacking subgoals and marking them complete, which is an alternative to a fixed state machine for more dynamic objectives.

Overall, Yuka gives you a foundation of proven behaviors and systems, and you can extend it with custom logic to fit your game. The library is MIT-licensed open source, so you can even dive into its code or modify it if needed.

## Integrating Yuka with Three.js

Because Yuka is a standalone “AI engine”, integrating it with Three.js (or any renderer) involves keeping Yuka’s world in sync with the visual scene. The typical architecture is: **update Yuka’s simulation each frame**, then **apply Yuka’s results to your Three.js meshes** (positions, rotations).

### Syncing Yuka Entities with Three.js Meshes

There are two common approaches to sync a Yuka agent (e.g. `YUKA.Vehicle`) with a Three.js object:

1. **Using `setRenderComponent`:** Yuka provides a built-in way to link a game entity to a render object. Every `GameEntity` (base class of Vehicle) has `entity.setRenderComponent(mesh, callback)`. The callback is a function you provide to update the render object’s transform each time Yuka updates the entity. For example:

   ```js
   const mesh = new THREE.Mesh(geometry, material);
   scene.add(mesh);
   vehicle.setRenderComponent(mesh, sync);

   function sync(entity, renderComponent) {
     renderComponent.position.copy(entity.position);
     renderComponent.quaternion.copy(entity.rotation);
   }
   ```

   Here `vehicle` is a Yuka Vehicle, and `mesh` is the Three.js mesh. Each frame after Yuka moves the vehicle, it calls `sync(entity, renderComponent)` to copy the Yuka entity’s position and rotation to the Three.js mesh. This keeps the mesh visually in the correct place and orientation. Using `setRenderComponent` is convenient because the syncing is handled internally during the Yuka update.

2. **Manual syncing:** Alternatively, you can update the Three.js object yourself. In this approach, you do **not** attach the mesh to Yuka at all. Instead, after updating Yuka’s world each frame, you loop over your entities and set the Three.js object transforms. This might look like:

   ```js
   entityManager.update(delta);
   // after updating Yuka:
   mesh.position.copy(vehicle.position);
   mesh.quaternion.copy(vehicle.rotation);
   ```

   This method is equally valid. In fact, Yuka doesn’t require you to pass meshes into it at all. Some developers prefer manual sync for flexibility or to avoid tying game logic to rendering. If you go this route, just remember to update **both position and rotation** so the mesh faces the direction of movement. Yuka’s `Vehicle.rotation` is a quaternion representing the orientation, which you can copy into the Three.js mesh’s quaternion.

In either case, it’s important to ensure that your Three.js models are oriented correctly relative to Yuka’s coordinate system. Yuka uses a right-handed coordinate system like Three.js, with (by default) the forward direction of a vehicle along the +Z axis in local space. If your model faces a different direction (say, +X), you might rotate it or adjust the forward vector. In the code above, for example, the car model was rotated `Math.PI/2` on Y-axis so that it aligned with Yuka’s notion of forward. After that, copying the quaternion ensures the model turns correctly as the vehicle turns.

### Game Loop and Performance Considerations

Yuka is designed to be updated every frame (or on a fixed timestep). You can use Three.js’s `Clock` or Yuka’s own time utility. The library provides `YUKA.Time` which can compute a delta time each frame and keep an internal clock. A typical game loop with Three.js + Yuka looks like:

```js
const time = new YUKA.Time();
function animate() {
  requestAnimationFrame(animate);
  const delta = time.update().getDelta();    // get time since last frame
  entityManager.update(delta);               // update all Yuka entities
  renderer.render(scene, camera);            // render Three.js scene
}
animate();
```

. Here `entityManager` is a `YUKA.EntityManager` that you’ve added all your game entities to. Calling `entityManager.update(delta)` advances the simulation: it will update every entity (vehicles update their steering and move, state machines execute, etc.). Yuka’s update will also invoke the `setRenderComponent` callbacks for each entity automatically, so by the time you render, all Three.js objects are in their new positions.

**Frame-rate and smoothing:** Yuka uses a simple Euler integration for motion; using the real `delta` time ensures the movement is frame-rate independent. However, very large `delta` (from a stutter) could cause a big jump, so it’s sometimes wise to clamp delta or use a fixed timestep loop for critical physics. Yuka’s steering can sometimes produce jittery orientation changes (especially ObstacleAvoidance making rapid small turns). To address this, Yuka offers a `vehicle.smoother` property where you can assign a `new YUKA.Smoother(windowSize)`. This will smooth out abrupt steering changes by averaging the last N frames of the steering force before applying it. In practice, if you see twitchy movement, setting `vehicle.smoother = new YUKA.Smoother(20 or 30)` can help dampen it.

**Performance with many agents:** If you have many AI entities (hundreds of ships, for example), updating all steering behaviors and doing collision checks can become heavy. Yuka provides tools to mitigate this:

* Use the **spatial index** feature. By assigning a `CellSpacePartitioning` to the EntityManager, neighbor queries and obstacle queries become much faster. You’d initialize it like: `entityManager.spatialIndex = new YUKA.CellSpacePartitioning(width, height, depth, cellsX, cellsY, cellsZ)`, configured to your world size. Yuka will then automatically place entities into cells and only check nearby cells for neighbors (this is especially beneficial for flocking and avoidance).
* Leverage Yuka’s **TaskQueue** for expensive computations. Yuka has a notion of tasks (see `YUKA.Task` and `YUKA.TaskQueue`) which can be used to offload work over multiple frames or threads. In the advanced navmesh example, tasks are used to perform pathfinding without stalling the main loop. While the details are beyond this overview, the existence of a task system means you could potentially run A\* pathfinding on a web worker or split a long computation (like computing a large flow field) into smaller steps to maintain frame rate.
* Use **Regulators** to throttle updates. Yuka includes a `YUKA.Regulator` (a utility with an `updateFrequency` and a `ready()` method) that helps ensure you don’t run certain logic too often. For example, you might only update an expensive sensory check or a strategic AI decision once every second instead of every frame. By checking `if(myRegulator.ready(delta)) { ... do AI logic ... }`, you can have, say, 60 FPS rendering but AI decisions at 10 FPS. This is a common game AI pattern to reduce CPU load, and can easily be applied to Yuka’s state machines or goals.

**Physics integration:** Yuka itself is not a physics engine – it does not automatically handle rigidbody physics or collisions with forces. If you use Three.js with a physics library (like Ammo.js or Cannon), you’ll have to integrate that with Yuka manually. Typically, Yuka’s steering will produce a desired velocity, and you would feed that into your physics body or vice versa. One suggested approach is to let Yuka handle the AI movement and then copy Yuka’s output velocity to your physics bodies each frame. Alternatively, use physics for movement and feed the physics-computed positions back into Yuka’s entities (so Yuka knows where things are). A Babylon.js forum discussion (applicable to Three.js as well) confirms this approach: *“update the positions/velocities of your YUKA vehicles before you call `entityManager.update()`, then update the physics bodies with the YUKA vehicles’ values and step the physics engine”*. The key point is Yuka doesn’t know about physics collisions – you must handle those (e.g., if a Yuka-controlled ship hits an asteroid, your game should detect it and perhaps change the AI state or steering). Yuka’s role can be to guide the ship’s target velocity, while a physics engine actually moves the ship and prevents interpenetration.

### Common Pitfalls and Quirks

* **Orientation syncing:** Ensure you copy the **quaternion** (or rotation) from Yuka entities to your Three.js meshes. If you only copy position, the object will move but not turn correctly. Using `setRenderComponent` with a proper callback (as shown above) is the safest way to not forget this.
* **Scaling and units:** Yuka doesn’t inherently know the scale of your world – it uses whatever units you give it. Make sure your speeds, distances, and sizes (boundingRadius, etc.) in Yuka correspond to the units in Three.js. For example, if your Three.js models are in meters, treat Yuka distances as meters too. The `boundingRadius` of obstacles and vehicles should be roughly their collision radius in Three.js units so that avoidance behaviors trigger at the right distance.
* **2D vs 3D movement:** As noted, some steering behaviors in Yuka assume movement on a plane (especially those derived from classic game AI textbooks aimed at characters on a ground). In space, you might want full 3D. You can often still use them — for instance, Seek, Flee, Pursuit are fully 3D (they work with 3D vectors). But **Wander** by default might choose a random point on a circle around the forward vector; you might tweak it to add vertical jitter. Yuka’s Alignment/Cohesion for flocking consider neighbors in 3D positions, but if you want aircraft to also align “up” vectors, you’d extend those. According to one user, *“wander behavior is only x,z (…some behaviors only 2D)… Fortunately it’s easy to extend”*. Keep this in mind for space games – you might extend or override behaviors to account for pitch/yaw movement.
* **Lack of certain AI systems:** Yuka focuses on steering, FSM, and goal-based AI. It does not natively have behavior trees or planning algorithms (beyond goal-driven and fuzzy logic). If your AI design uses behavior trees, you’d have to implement that on top or use FSM/Goal as an alternative. There is no built-in support for learning or advanced strategies (no built-in support for things like neural nets or Markov models – you’d implement those separately and then integrate via states or goals).
* **Debugging:** Yuka doesn’t directly provide visual debugging tools (it doesn’t draw lines or gizmos in Three.js for you), but you can always use Three.js helpers to visualize things like paths (e.g. draw a line through waypoints), vision cones, or steering forces for debugging. Since Yuka’s data (positions, vectors) are accessible, it’s straightforward to add your own debug visualization if needed.
